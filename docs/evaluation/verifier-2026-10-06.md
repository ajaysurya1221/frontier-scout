# `verify-pr` repair: defect matrix and regression results (2026-10-06)

Frontier Scout is a research preview. This note records five false acceptance paths found in
`frontier_scout/agent_firewall/verify.py` at `b9abe24` (`main`, 2026-10-05), the repair, and the
real-git tests that reproduce each path on the old code and reject it on the new one. It also
compares the scope and evidence-trust model with four related projects, using only their
published READMEs.

**What the repaired verifier claims.** For a PR diff (`<base>...HEAD`, collected by the verifier
with `git diff --name-status -z -M`), every changed path, both ends of a rename included, is
checked against the policy and lock read from the base commit. Anything the verifier cannot
establish is reported as not passing.

**What it does not claim.** Receipts are unsigned JSON written on the machine the agent
controls. They cannot show who approved a protected change, so the verifier never treats
them as approval. A changed protected path is always FAIL (no receipt) or UNVERIFIED (unsigned
receipt only), never PASS. Approving such a change is a human decision outside this tool.

Releases up to and including **v2.1.0** (PyPI and the `@v2.1.0` Action tag) contain the defects
below. The repair was unreleased at the time of writing and ships in **2.2.0**.

## Regression matrix

All 40 tests are in `tests/test_verify_regression_matrix.py`: 38 repository cases, one parser
unit test and one documentation test. Each repository case builds a temp repo with real
commits, and the verifier runs the real `git` itself. The first assertion of each bypass case
is `res.ok is False`. "Old" is the result with `verify.py` from `b9abe24`; "new" is this repair.
To reproduce the old column, swap the old file in and run the module:

```bash
cp frontier_scout/agent_firewall/verify.py /tmp/verify.new.py
git show b9abe24:frontier_scout/agent_firewall/verify.py > frontier_scout/agent_firewall/verify.py
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python -m pytest -q tests/test_verify_regression_matrix.py
cp /tmp/verify.new.py frontier_scout/agent_firewall/verify.py
```

## Before and after, by situation

| Situation | Before (`b9abe24`) | After |
|---|---|---|
| In-scope change, no receipts | PASS + warning | PASS + `RECEIPT_ABSENT` warning |
| Path outside `allowed_file_globs`, not protected | PASS + warning | FAIL |
| Protected path, no receipt | FAIL | FAIL |
| Protected path, local or PR-committed receipt (any decision or approval field) | PASS | UNVERIFIED (exit 1 when enforcing) |
| Path changed despite a `deny` receipt | FAIL | FAIL |
| Receipt with no policy hash / stale hash / unparseable | PASS / FAIL / skipped | FAIL / FAIL / FAIL |
| PR edits the policy and lock to widen its scope | PASS | FAIL: the base policy governs, and the edit is a protected change |
| Lock missing at the base but added by the PR | PASS (working-tree lock used) | FAIL `POLICY_LOCK_MISSING` |
| Lock without a hash, or schema-invalid policy | PASS / PASS | FAIL / FAIL |
| No `--base`, failed diff, option-shaped base | PASS / UNVERIFIED / PASS | UNVERIFIED / UNVERIFIED / UNVERIFIED |
| Advisory mode with findings | `PASS: …`, exit 0 | `<VERDICT> (advisory: reported, not enforced): …`, exit 0 |

The CLI exits 0 only for PASS in enforcing mode, and always exits 0 in advisory mode. The
summary line reports scope and approval provenance separately, for example
`UNVERIFIED: scope verified (…); approval provenance not authenticated for 1 protected path(s) (receipts are unsigned); …`.
The JSON result carries `verdict`, `scope` (`verified | violated | not-evaluated`),
`approval_provenance` (`not-required | unauthenticated | not-evaluated`), `policy_source`,
`receipts_in_pr`, `reason_codes` and `findings`.

## What is still not verified

1. **Approval provenance.** Nothing in this repository authenticates who approved a protected
   change. Such PRs stay non-green when enforcing, and a human has to approve them outside the
   tool (for example through branch-protection review, or by an admin merging past the check).
   Authenticated approval provenance is deferred.
2. **The workflow runs on `pull_request`.** For that event GitHub runs the workflow file from
   the PR. A PR can therefore edit or delete the verify step, or change the pinned install
   line, and the verifier never sees it. `.github/workflows/**` is protected by default, but
   that only matters if the verifier runs. To enforce the check, run it from a workflow the
   PR cannot edit: for example, a required workflow in an organization ruleset pinned to a
   trusted ref, or `pull_request_target` with a checkout that never executes PR code. This
   repair does not change the trigger.
3. **This repository's own dogfood workflow** installs the PR's source (`pip install .`,
   `uses: ./`) on purpose, to exercise the code under review. It runs in advisory mode and is
   not a gate.
4. **Base trust.** The verifier trusts the `--base` it is given. The Action derives it from
   `GITHUB_BASE_REF`; a caller that passes a PR-controlled ref defeats the base-policy rule.
5. **Glob semantics** are the hook's (`_path_matches_glob`): `fnmatch` with suffix matching and
   case-sensitive names, and `*` crosses `/`. `tests/**` also matches `pkg/tests/x`, and
   `*.toml` matches at any depth. CI and the hook agree, but policy authors should know this.
6. **Content is not inspected.** Symlinks are checked by their own path, not their target.
   Copy detection is off, so a copied protected file appears as an addition at the
   destination. File contents are never read, so there is no secret scanning of the diff.
7. **Committed receipts are PR content.** A receipt committed under `frontier-scout-receipts/`
   must itself be inside `allowed_file_globs`, or it is `SCOPE_OUTSIDE_ALLOWED`. Receipts can
   also be supplied with `--receipts` from outside the PR, for example a downloaded artifact.
8. **Action isolation was tested under a simulated runner**, by executing the run steps from
   `action.yml` with bash and the step environment, not on GitHub-hosted runners. In those
   tests the `version: ""` install branch (building from `$GITHUB_ACTION_PATH`) is checked
   statically only. The `action-source-install` job in `.github/workflows/ci.yml` runs that
   branch on a GitHub-hosted runner: the action source and the candidate are separate
   checkouts, shadow modules sit in the workspace and candidate roots, and the job fails if
   one is imported, if the installed version differs from the action source, or if the
   verdict on an empty diff is not pass. It does not repeat the simulated tests'
   `PYTHONPATH` injection or their FAIL-path checks.
